DAST scanner

File Upload

An upload endpoint that accepts anything lets an attacker plant a script on your domain or write outside the upload folder. The scanner finds endpoints whose path looks like an upload, posts an HTML file, an SVG file and three traversal filenames as multipart form data, and judges each by one thing: did the server answer 2xx.

Finding upload endpoints

The scanner does not look at forms or methods. It reads the path of every endpoint in the inventory and keeps the ones that contain an upload word.

1The scanner starts from the endpoint inventory built by discovery and the crawl: method and URL for every endpoint.

2An endpoint is kept if its lowercased path contains one of eight words: /upload, /file, /media, /attachment, /image, /avatar, /document, /import. Method, form fields and content type are not consulted.

3The kept list is what gets probed. Because the match is a substring, a read-only GET /files/list is included, and an upload sink on a path like /api/orders is never tested.

The five probes

For every kept endpoint the scanner posts five small files, one at a time. Two test which file types the server accepts. Three test whether it accepts a filename that climbs out of the upload folder.

1Each probe is a multipart POST with a single part named file, carrying a filename, a part content type and a tiny body. The session's auth headers are attached when the scan has a session.

2Type probes. test.html (text/html) and test.svg (image/svg+xml), each with a script payload. A 2xx for either is a High finding titled "File upload accepts dangerous file types", because an uploaded HTML or SVG file served back runs script on your origin.

3Traversal probes. A harmless test body under three filenames in order. The first 2xx is a Critical finding, "File upload vulnerable to path traversal", and the remaining names are skipped for that endpoint.

4The decision rule is the status code and nothing else. Anything from 200 to 299 is "accepted". A 4xx, a 5xx or a failed connection is not.

What a 2xx does and does not prove

Because the rule reads only the status, the finding means "the server did not refuse this". It is a strong lead, and sometimes a false alarm. The four replies below show where the line is.

1A refusing server answers 4xx. No finding, no noise.

2A server that stores the file answers 2xx, often with a URL. That is the finding. The scanner never opens the URL to check how the file is served or whether a traversal name escaped the folder.

3Some APIs return 200 and put the refusal in the JSON body. The scanner reports these too, since it never reads the body, so treat a High finding as "verify this upload by hand".

4The part is always named file. An endpoint that requires a different field name rejects every probe and is silently skipped.

Why it matters

Impact

Unrestricted file uploads let an attacker:

  • Execute code on your server. Uploading .php, .jsp or .sh files that the server executes.
  • Plant stored XSS. An .html or .svg file with JavaScript runs when someone opens it on your domain.
  • Overwrite system files. A traversal name such as ../../etc/cron.d/backdoor can write anywhere the process can.
  • Serve malware. Your domain becomes a malware distribution point.

Real-world breach

ImageTragick · 2016

CVE-2016-3714 in ImageMagick allowed remote code execution via crafted image files. Any service that accepted user-uploaded images and processed them with ImageMagick was vulnerable.

The fix: three gates before the file is saved

Check the extension, check the declared type, and never use the client's filename. Watch three uploads go through.

1The happy path. The file is checked on extension and declared type, then stored under a name the server chose.

2Gate one: extension allowlist. .svg, .html and the other dangerous types are not on it, so the scanner's type probes get a 400.

3Gate three removes traversal at the root. A random UUID name means the filename the client sent never touches the filesystem, so ../ has nothing to climb with.

Vulnerable vs fixed

// BAD: accepts any file and keeps the client's filename
export async function POST(request: Request) {
  const file = (await request.formData()).get("file") as File
  await fs.writeFile(path.join(UPLOAD_DIR, file.name), Buffer.from(await file.arrayBuffer()))
  return NextResponse.json({ url: `/uploads/${file.name}` })
}
// GOOD: Whitelist allowed extensions and validate content
const ALLOWED_TYPES = ["image/jpeg", "image/png", "image/webp"]
const ALLOWED_EXTENSIONS = [".jpg", ".jpeg", ".png", ".webp"]

export async function POST(request: Request) {
  const file = formData.get("file") as File
  const ext = path.extname(file.name).toLowerCase()

  if (!ALLOWED_EXTENSIONS.includes(ext)) {
    return NextResponse.json({ error: "File type not allowed" }, { status: 400 })
  }
  if (!ALLOWED_TYPES.includes(file.type)) {
    return NextResponse.json({ error: "Invalid content type" }, { status: 400 })
  }

  // Generate a random filename (prevents path traversal)
  const safeFilename = `${crypto.randomUUID()}${ext}`
  // ... save with safeFilename
}
