How this group works

Every injection scanner is a marker and an oracle. The marker is what the scanner puts into the app; the oracle is the one signal it reads back. The lanes below are the six scanners in this group, one per row, and the columns switch on in the order the scanner moves through them.

1Six scanners, one shape. Each starts from a place where outside data enters: a query, body or path parameter, a form field, a filename, a URL the server will fetch, or, for the static analyzer, a request object in the code.

2Each sends a marker it can recognise later: a quote that breaks SQL, the cloud metadata address, a canary wrapped in angle brackets, a traversal filename. Taint analysis sends nothing; it marks the variable that holds request data and follows it.

3The target processes the marker. Everything goes through one rate-limited client, read-only payloads only, and every scanner checks its time budget per endpoint so it returns what it has instead of being cancelled.

4Each scanner reads one specific signal: a database error string or a delay, metadata text or an out-of-band callback, the canary with its brackets intact, a hooked browser sink, a 2xx with evidence the file was stored, a sink call in code.

5The rule: report only when the signal is specific to the marker. Canary text alone is not enough, the brackets must survive; a one-off delay is not enough, it must reproduce; a sink name in a bundle is not enough, the canary must arrive in a real browser. File upload needs more than a 2xx: the body must not be a failure and the stored file or name must be visible.

6Every finding lands in one category, Injection Risk. That is what lets the correlator pair a dynamic hit with a static taint path on the same route and raise both to a confirmed finding.

Why this class matters

Why injection

Injection is the attacker's input being interpreted as code or as a command by something on your side: the database, the shell, the XML parser, the template engine, the browser, the filesystem. The impact is whatever that interpreter can do. SQL injection reads or rewrites the whole table. XSS runs JavaScript as your users, which means their tokens, their actions and any form on the page. SSRF turns the server into a proxy to the cloud metadata service that hands out IAM credentials. An accepted .svg upload is stored XSS on your own domain, and an accepted traversal filename is a write anywhere on the filesystem.

Real-world breaches

Heartland Payment Systems, 2008

SQL injection led to the theft of 130 million credit and debit card numbers, one of the largest breaches in history at the time.

Capital One, 2019

An SSRF vulnerability in a WAF configuration reached the AWS metadata endpoint (IMDSv1), yielded IAM credentials, and exposed 100+ million customer records from S3. Capital One was fined $80 million.

British Airways, 2018

The Magecart group injected malicious JavaScript into the payment page and skimmed 380,000 customers' card details. The ICO fined BA $26 million. There was no Content Security Policy and user input was rendered without sanitization.

ImageTragick, 2016

CVE-2016-3714 in ImageMagick allowed remote code execution via crafted image files. Any service that accepted user-uploaded images and processed them with ImageMagick was vulnerable.
