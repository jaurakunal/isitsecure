Architecture

Triage and Grading

Scanners report one finding per affected location, which is right for detection and unreadable as a report. Phase 9.5 shrinks the list by rule, asks an LLM what each survivor would cost and how easily it could be exploited, lifts the severity of anything both financial and live, and writes the summary a site owner will actually read.

Stage 0: four passes, no LLM

Deduplication is a rule about where a fix goes, so it needs no model and costs nothing. It used to sit behind the LLM triage phase, which meant a scan run with --llm none shipped the raw list: 296 findings on Juice Shop, of which 272 were five issues restated once per endpoint. It now runs first, with or without an API key. The example below is thirteen findings; follow the right-hand counter.

1Thirteen findings arrive, one per location. Four scanners reported the same missing header on four URLs, two IDORs share a title, a Stripe key was found twice on one line and three times in one file, and two dependency scanners described the same package differently.

2Pass 1: exact title. Lower-cased, trimmed titles group together. The group keeps its best finding (highest severity, then an LLM-reviewed one, then the longest description) and appends "Affects 4 endpoints: …". Categories whose fix is per location are keyed by title plus location, which is why the two IDORs are not a group.

3Pass 2: same file and line. Two scanners, the secret scanner and the git-history scanner, flagged config.ts:12. One source line is one fix, so the best of the two is kept. For per-location categories the endpoint is part of the key, so a shared handler reached from two routes stays two findings.

4Pass 3: same SAST scanner, category and file, three or more. Three Stripe values in lib/pay.ts become one finding that lists the others. This pass only applies to the deterministic SAST scanners; two LLM findings in one file are usually different issues and are left alone.

5Pass 4: fuzzy title. Titles are reduced to words of three or more letters minus stop words; both need at least three. Overlap is measured against the larger set, and 60% or more merges. "vulnerable, jsonwebtoken, cve" against "vulnerable, package, jsonwebtoken" is two of three. Two live findings on different endpoints never fuzzy-merge, and per-location categories never merge across locations.

6Six findings leave Stage 0, each still pointing at every place it was seen. The pass that produced the Juice Shop number was not a smarter rule; it was running the rules at all when no LLM key is present.

Remediation scope decides how a pass behaves

RemediationScope answers one question per category: how many places does the fix go? Every pass consults it, the fuzzy pass included, because that one is the loosest and a wrong merge there is both most likely and least visible.

1A category's scope is set once in code. Scanners keep reporting per location; the scope tells each dedup pass whether those locations are one problem or many.

2SERVER. Missing headers, CORS, mixed content, source maps and SRI are one setting on one server. Reported once, and the list of endpoints it was seen on is kept as evidence: 76 URLs says "the server has no CSP", which is what makes the single fix worth doing.

3INSTANCE. IDOR, injection, auth, privilege escalation, business logic and open redirect are each somebody writing a check in a specific place. Every occurrence is kept and never collapsed across locations. A category with no scope assigned defaults here, the safe direction.

4SHARED_ROOT. Exposed secrets, dependencies, RLS and client exposure have one cause reached from many places: rotate the key, bump the package, write the policy. Grouped under the cause, with the sites listed.

5Failure mode one. Without the scope, dedup on title alone was the only option, and turning it off meant "Missing Content-Security-Policy" restated on 76 endpoints. The real finding is on page four.

6Failure mode two. Dedup on title alone does the header case correctly and this one silently: four IDORs on four endpoints share a title, so three of them vanish behind something that looks handled. The two modes point opposite ways, which is why one rule cannot serve both.

Stage 1: impact × likelihood → priority, then calibration

Findings that still need judgement go to the LLM in batches of twenty, up to three batches at a time. For each one it returns an impact category and a likelihood level, and the priority is read from a fixed table. Findings from the deterministic SAST scanners never make the trip: their impact comes from a category table and their likelihood from their severity.

1The table is fixed in code. Rows are the five impact categories, columns the four likelihood levels, cells the priority. The LLM's job is to place each finding; the priority is never asked of the model.

2A SQL injection on a public search endpoint: the model says data_breach and actively_exploitable. The cell reads 1, the highest priority.

3A missing CSRF token on an admin-only form: operational impact, exploitable only with an admin already logged in. Priority 3.

4A version string in the Server header: reputational, theoretical. Priority 4. Any pair the table does not list falls back to 3.

5Deterministic SAST scanners are placed by rule, with no LLM call: impact from the category (unknown categories count as operational), likelihood from severity. Anything the LLM batch skipped or timed out on gets the same rule-based placement, so nothing leaves triage without a priority.

6Stage 1.5 calibration. After enrichment, any finding still rated HIGH whose impact is financial or data_breach and whose likelihood is actively_exploitable is lifted to CRITICAL with priority 1. The two red cells are the only ones that trigger it. MEDIUM findings are never jumped.

Stage 2: the owner summary and the grade

One small LLM call receives the severity counts and a compact serialization of the findings and returns a summary for someone who does not read code: a plain-language risk statement, a letter grade, up to five key risks, and a remediation plan in phases. The headline grade on the report itself is computed by rule from the severity counts, on the ladder shown on the right.

1The prompt carries the scan mode, the target, the totals of critical, high and medium findings, and a compact JSON of the triaged list. The model is asked for a fixed JSON shape in return.

2Risk summary and grade. A sentence or two a site owner can act on, and a letter from A to F. The letter here is the model's; if the call fails, a count-based fallback grades A with no critical or high, B with at most two high, C with at most five, D with at most one critical and ten high, F beyond that.

3Key risks. Whatever the model lists is cut to five. Each is meant to be readable without the finding it came from.

4Phased plan. The model names the phases; the counts are filled by rule so they always add up: CRITICAL and HIGH findings in phase 1, MEDIUM in phase 2, LOW in phase 3. Each finding belongs to exactly one phase.

5The report grade does not come from the model. calculate_grade walks the ladder from the top and stops at the first rung that matches: any critical is F regardless of everything else. The example counts land there. If a scanner timed out or crashed (recorded in scanner_errors), the verdict reads "scan incomplete" and the grade is labelled provisional, unless critical or high findings already decide it.

6Fix the critical and both highs and the same ladder gives C+: no critical, no high, two medium is fewer than three. The report also lists these steps as "what it takes to reach the next grade", computed from the same thresholds.

Why it matters

The raw list is the wrong unit

A scanner is right to emit one finding per URL: that is where it saw the problem. A report built from that list is wrong twice over. Collapse by wording and three of four IDORs disappear; refuse to collapse and one missing header fills four pages. The scope rule exists because those two mistakes point in opposite directions, and the measured Juice Shop list, 296 findings of which 272 were five issues restated per endpoint, is what the first mistake looks like at scale.

Severity is not priority

Severity says how bad the bug class is. Priority says what to fix this week, which depends on who can reach it and what it costs the business. The matrix makes that a table lookup, and calibration catches the one combination, live and financial or data-exposing, where a HIGH label would understate a breach already in reach.
