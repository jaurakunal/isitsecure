Scanner group

Access control

Every scanner in this group works from one kind of evidence: a request sent by a principal who should have been refused, and the response that came back. The principal is anonymous, a second user, a regular user instead of an admin, or a client sending a field it was never meant to control. The scanner then reads the body, because a 200 on its own proves nothing.

How this group works

Four principals, three resources, one loop. Each step below is one scanner from the group sending its characteristic request. Watch which principal sends it, what comes back, and what in the response turns a reply into a finding.

1Three principals and three resources. Each scanner picks the principal that should be refused and sends the request a more privileged principal is allowed to send. The decision is always made on the response body, never on the status alone.

2IDOR. User B asks for task 42, which belongs to User A. A 200 is only a finding if the body carries User A's data, and only if an anonymous request for the same id was refused; otherwise the object is public and nothing is wrong.

3Privilege escalation. The regular user requests a path that matches an admin indicator. A 200 is the finding. With two accounts the scanner also compares the admin's and the regular user's replies to the same GET, and flags only when the admin's is more than 1.5 times larger and holds more records.

4Mass assignment. A bare body with one escalation field goes to every POST, PUT and PATCH endpoint. The finding needs a 2xx and the same field with the same value somewhere in the reply, however deep the envelope.

5Body param fuzzer. A write that User A really sent during the crawl is replayed with one field replaced. A database error pattern, a verbatim reflection, a 5xx on a wrong type, or a __proto__ key accepted without a 400 each make a finding.

6The static side. Route auth tracing reads the handler for a guard and follows it to its definition. The RLS policy analyzer reads the migrations; the RLS deep scanner asks the live table with the public anon key. When a DAST and a SAST finding of a paired category land on the same app, correlation raises both.

Why this class matters

Why it matters

Access control bugs do not need a payload. The request is well formed, the server is working as written, and the only thing wrong is who was allowed to send it. Privilege escalation turns a free account into full admin access: every record, every setting, every delete, and new admin accounts for persistence. Mass assignment lets a client promote itself, zero a price or mark an order paid by adding a field. An IDOR hands one user another user's data by changing a number. None of these show up in a crash log.

Real-world breaches

Microsoft Exchange, ProxyLogon (2021). CVE-2021-26855 let attackers authenticate as the Exchange server, escalate to admin and install web shells across tens of thousands of organisations. GitHub (2012). Egor Homakov used a Rails mass assignment flaw to attach his SSH key to the Rails core repository by setting user_id, gaining commit access. HackerOne (2015). A mass assignment flaw allowed adding yourself as a member of any bug bounty program by manipulating group membership parameters.
