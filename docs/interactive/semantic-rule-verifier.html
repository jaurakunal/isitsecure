Semantic Rule Verifier

The structural analyzers can tell you that a table has a policy. They cannot tell you the policy compares the user's id to the task's own primary key. This scanner gives each RLS migration and Firebase rules file to a model and asks only one question: is the logic of these rules wrong?

What is sent, what comes back

One model call per file. The scanner decides which files qualify with plain string matching, so the model never sees a file that is not about access rules.

1Collect. A .sql file is sent if its text contains CREATE POLICY or ENABLE ROW LEVEL SECURITY. A file is sent as Firebase rules if its name ends in firestore.rules, storage.rules or database.rules.json. Everything else stays local.

2Send. Each qualifying file becomes one prompt: a system message naming the flaws to look for, and the file path plus its first 50,000 characters. The model is asked for a JSON array.

3Reply. Each flaw comes back as severity, title, description, line number and remediation guidance. The prompt tells the model to ignore missing policies and open rules, which the structural analyzers already report.

4Parse. The scanner takes everything from the first [ to the last ], parses it, keeps at most seven objects, and builds each finding with its own fixed confidence of 0.70.

5Absent or failing. Without an API key the scanner is not registered at all. If a call errors or the reply is not JSON, that file yields nothing and the scan continues.

A policy that looks right

The example from the scanner doc. A regex scanner sees ENABLE ROW LEVEL SECURITY and a CREATE POLICY and is satisfied. The mistake is in one comparison.

1A migration with RLS switched on and one SELECT policy. Both structural checks pass: the table is protected and a policy exists. The comparison on the last line is the question.

2The structural RLS analyzer finds nothing here. It answers whether policies exist, and they do.

3The model reads the whole file. It can see id is the primary key and user_id is the owner column, so it knows auth.uid() = id compares the wrong things.

4The reply becomes a finding with the model's title, description, severity and line number, and a fixed confidence of 0.70. The other flaw classes it looks for are privilege escalation paths, uneven operation coverage and tenant isolation errors.

5The limit of this approach: the prompt holds only the one file. If the table and its columns were created in an earlier migration, the model sees the policy without the schema and has less to judge with.

What guards the output

Model text is never used as a finding as it arrives. It passes four checks, and what the code does not check is listed last.

1No key, no call. The verifier is registered only when an LLM client exists. Without one the scan runs every rule-based scanner and none of this.

2Extract. The reply is searched for a JSON array. Missing or malformed gives an empty result for that file. An exception from the call is logged and swallowed.

3Per item. At most seven items per file. Non-objects are skipped. A severity the code does not recognise is treated as MEDIUM.

4Confidence is not the model's to set. Every finding gets 0.70 and the fixed RLS misconfiguration category, so triage treats all of them alike.

5Never auto-trusted. Nothing re-tests the claim, and the line number is not checked against the file. The doc says the model supplies fix suggestions per finding, but the code requests them and does not store them.

Why it matters

Why it matters

A policy that looks correct but references the wrong column is worse than no policy: it gives false confidence while being bypassable or broken. The scanner looks for four kinds of logic error: a wrong column in the auth.uid() check, a combination of policies that allows escalation (for example a user updating their own role), a SELECT policy with no matching UPDATE or DELETE policy, and multi-tenant policies that do not scope to the tenant. For Firebase rules it looks for auth checked on the wrong path, writes protected while reads leak, custom claims checked loosely, and rules that let one user overwrite another's document by predictable id.

Real-world context

Facebook (2013). The ability to delete any photo was caused by the API checking whether the photo id existed rather than whether the requester owned it. An RLS policy checking auth.uid() = id instead of auth.uid() = user_id is the same class of bug: the check runs, it just asks the wrong question.

Vulnerable vs fixed rules

The same pairs the scanner doc lists. The fix is a different comparison or fuller operation coverage, not more policies.

-- LOOKS correct but IS wrong:
CREATE POLICY "Users view own tasks" ON tasks
  FOR SELECT USING (auth.uid() = id);
-- id is the TASK's primary key, not the owner's id
-- CORRECT: compare to the foreign key column
CREATE POLICY "view own" ON tasks
  USING (auth.uid() = user_id);
-- WRONG: SELECT only, no INSERT/UPDATE/DELETE policy
-- CORRECT: cover every operation
CREATE POLICY "crud own" ON tasks
  FOR ALL USING (auth.uid() = user_id)
  WITH CHECK (auth.uid() = user_id);
